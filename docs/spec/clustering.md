# Multi-Node Clustering Specification

**Status:** Complete

## Overview

inframatik supports a master/worker clustering model where a single master node acts as the central dashboard for multiple machines. Workers register with the master, send heartbeats, and the master proxies API requests to workers on behalf of the browser. The system uses in-memory node tracking, enrollment tokens for secure onboarding, and a deploy mechanism to push code updates from master to workers.

## Requirements

1. **Three roles** -- Nodes can be standalone (single machine), master (central), or worker (satellite).
2. **Enrollment tokens** -- One-time tokens generated by the master to authorize worker registration.
3. **Heartbeat monitoring** -- Workers heartbeat every 15 seconds; master marks stale nodes after 45 seconds.
4. **Transparent proxy** -- Browser always talks to the master; master forwards requests to workers.
5. **Code deployment** -- Master can package and push its code to all workers, then restart them.
6. **Installer script** -- `curl | bash` installer that bootstraps a new machine and optionally enrolls as a worker.
7. **Role transitions** -- Standalone can upgrade to master or switch to worker. Reset returns to unconfigured.

## Node Roles

| Role | Description | Background Task | API Key |
|------|-------------|-----------------|---------|
| `standalone` | Single machine, no clustering | None | None |
| `master` | Central dashboard, manages workers | `stale_checker_loop` (every 10s) | Generated on init (for workers to identify) |
| `worker` | Satellite node, reports to master | `heartbeat_sender_loop` (every 15s) | Received from master during enrollment |
| `unconfigured` | No node.json file exists | None | None |

### Role Transitions

```
unconfigured -> standalone (POST /api/config/init-standalone)
unconfigured -> master     (POST /api/config/init-master)
unconfigured -> worker     (POST /api/config/init-worker)
standalone   -> master     (POST /api/config/init-master)
standalone   -> worker     (POST /api/config/init-worker)
any          -> unconfigured (POST /api/config/reset)
```

Master and worker roles cannot transition directly to each other without a reset first.

## Enrollment Flow

### Token-Based Enrollment (UI)

```
1. Master admin generates enrollment token
   POST /api/config/enrollment-tokens -> {token: "enroll-..."}

2. On new machine, admin enters master URL + enrollment token in setup wizard

3. Worker calls master's enrollment endpoint:
   POST {master}/api/nodes/enroll {token, node_name, address}
   -> Master validates token (one-time, consumed on use)
   -> Master generates api_key for the worker
   -> Master stores worker in its config (workers dict)
   -> Returns {api_key, signing_public_key, cf_config?}

4. Worker configures itself locally:
   POST /api/config/init-worker {name, master_url, api_key, cf_config?}
   -> If cf_config is present, worker saves it, creates its own CF tunnel,
      starts local cloudflared, and reports tunnel_id back to the master.

5. Worker process restarts, heartbeat_sender_loop begins
```

### Installer Enrollment (CLI)

```
curl -sSL http://master:9000/api/install.sh | bash -s -- \
  --enroll <token> --name <node-name> --password <admin-pw>

1. Script downloads code package from master
2. Sets up Python venv, installs deps
3. Creates systemd service, enables linger
4. Sets admin password via local API
5. Calls POST {master}/api/nodes/enroll with token
6. Receives api_key from master
7. Calls POST localhost:9000/api/config/init-worker with credentials
8. Restarts service so heartbeat loop picks up worker config
```

### Enrollment Token Properties

- Format: `enroll-` + 16 random hex bytes (32 hex chars)
- Stored in master's node.json under `enrollment_tokens` dict
- One-time use: consumed (deleted) on successful enrollment
- Can be manually deleted before use via `DELETE /api/config/enrollment-tokens/{token}`
- Contains `created_at` timestamp

## Heartbeat System

### Worker Side (`heartbeat_sender_loop`)

Launched as a background asyncio task during FastAPI lifespan when role is `worker`.

**Registration phase:**
1. Determine local routable IP by opening a UDP socket toward the master host
2. Build registration payload: `{node_id, node_name, address: "http://{ip}:{port}"}`
3. POST to `{master}/api/nodes/register` with `X-Api-Key` header
4. Retry with exponential backoff: 5s initial, doubles each failure, capped at 30s
5. After 10 consecutive failures, log a warning

**Heartbeat phase:**
1. Sleep 15 seconds
2. POST to `{master}/api/nodes/heartbeat` with `{node_id}`
3. If master returns 404 (node not registered), re-register
4. On network errors, silently retry on next iteration

### Master Side

**Registration handler** (`POST /api/nodes/register`):
1. Validate `X-Api-Key` against configured workers
2. Store node in `_nodes` dict with: node_name, address, status "online", last_seen, registered_at, config_node_id
3. Update `_id_map` for both real node_id and config-key node_id

**Heartbeat handler** (`POST /api/nodes/heartbeat`):
1. Look up node_id (via `_id_map` if needed)
2. Update `last_seen` timestamp and set status to "online"
3. Return 404 if node not in registry (triggers re-registration)

**Stale checker** (`stale_checker_loop`):
1. Runs every 10 seconds as a background asyncio task
2. For each node in `_nodes`, if `time.time() - last_seen > 45s`, set status to "offline"

### Health Check Fallback

For workers that are in the master's config but haven't registered (heartbeated) yet, the master actively probes:
1. `GET {worker}/api/node/health` (preferred)
2. Fallback: `GET {worker}/api/system` (for workers without cluster code)
3. Results cached for 15 seconds per worker address

## In-Memory Node Registry

### `_nodes` Dict

```python
_nodes: dict[str, dict] = {
    "a1b2c3d4": {  # real node_id from the worker
        "node_name": "gpu-server",
        "address": "http://192.168.1.20:9000",
        "status": "online",       # "online" or "offline"
        "last_seen": 1709856000.0,
        "registered_at": 1709855000.0,
        "config_node_id": "e5f6a7b8",  # key in master's workers config
    }
}
```

### `_id_map` Dict

Maps any form of node_id to the real node_id in `_nodes`:

```python
_id_map: dict[str, str] = {
    "a1b2c3d4": "a1b2c3d4",  # real -> real (identity)
    "e5f6a7b8": "a1b2c3d4",  # config_key -> real
}
```

This allows the UI to reference nodes by either ID format. The master's config uses its own generated IDs (from `add_worker`), while workers report their own `node_id`.

## Proxy System

### `proxy_to_node(node_id, method, path, body)`

1. Call `resolve_node(node_id)` to get connection info
2. If returns `None` -- this is the self-node, call `_handle_local()` instead
3. Otherwise, make HTTP request to `{address}{path}` with `X-Api-Key` header
4. Support GET, POST, DELETE methods
5. Timeout: 10 seconds

### `resolve_node(node_id)`

Priority order:
1. If `node_id == config["node_id"]` -- return `None` (self)
2. Check `_id_map` -> `_nodes` for registered workers -- return `{address, api_key}`
3. Check config `workers` dict for unregistered workers -- return `{address, api_key}`
4. Raise `ValueError("Unknown node")`

### `_handle_local(method, path, body)`

Routes proxied requests to local Python functions when the target is the master itself:

| Route | Function |
|-------|----------|
| `GET /api/system` | `get_system_metrics()` |
| `GET /api/services` | `list_services()` |
| `POST /api/services` | `register_service(...)` |
| `DELETE /api/services/{name}` | `deregister_service(name)` |
| `POST /api/services/{name}/{action}` | `start/stop/restart_service(name)` |
| `GET /api/services/{name}/logs` | `get_service_logs(name, lines)` |
| `GET /api/tunnel` | `get_tunnel_status()` + `get_tunnel_routes()` |

### Proxied API Endpoints

| Master Endpoint | Worker Endpoint |
|----------------|-----------------|
| `GET /api/nodes/{id}/system` | `GET /api/system` |
| `GET /api/nodes/{id}/services` | `GET /api/services` |
| `POST /api/nodes/{id}/services` | `POST /api/services` |
| `DELETE /api/nodes/{id}/services/{name}` | `DELETE /api/services/{name}` |
| `POST /api/nodes/{id}/services/{name}/{action}` | `POST /api/services/{name}/{action}` |
| `GET /api/nodes/{id}/services/{name}/logs` | `GET /api/services/{name}/logs` |
| `GET /api/nodes/{id}/tunnel` | `GET /api/tunnel` |

## Deploy System

### Build Package

`build_package()` creates a tar.gz archive of the app source:
- Includes: `*.py` files, `static/*`, `requirements.txt`, `install.sh`
- Excludes: `venv/`, `__pycache__/`, `.git/`, `.env`, `node.json`
- Maximum package size enforced on receive: 50MB

### Push to Workers

`POST /api/update/deploy` (master only):
1. Build package from local source
2. For each worker in config, POST package bytes to `{address}/api/node/update`
3. Worker validates API key, extracts tar over app directory (with path traversal protection)
4. Worker schedules restart after 1 second (so response is sent first)
5. Master collects results per worker

### Worker Update Handler

`POST /api/node/update`:
1. Validate `X-Api-Key` matches worker's configured key
2. Read request body (max 50MB)
3. Extract tar.gz with path safety check (`is_relative_to(APP_DIR)`)
4. Schedule `systemctl --user restart inframatik` after 1 second
5. Return `{status: "updated"}`

### Self-Restart

`POST /api/update/deploy-self`:
- Schedules `systemctl --user restart inframatik` after 1 second
- Returns immediately with `{status: "restarting"}`

## Install Script

Served by the master at `GET /api/install.sh` with `__MASTER_URL__` placeholder replaced by the actual master URL (derived from the request's Host header).

### Arguments

| Flag | Description |
|------|-------------|
| `--enroll <token>` | Enrollment token for automatic worker registration |
| `--name <name>` | Node name (defaults to `hostname -s` if enrolling) |

### Script Steps

1. Validate prerequisites: `python3`, `curl`, `sudo`
2. Verify not running as root (must run as regular user with sudo)
3. Download and extract code package from master
4. Create Python venv, install pip dependencies
5. Create config directory (`~/.config/inframatik/`)
6. Optional: install `cloudflared` binary to `~/.local/bin/cloudflared` (checksum-verified, no sudo)
7. Add `ports.env` sourcing to `.bashrc`
8. Create systemd user service for inframatik (port 9000)
9. Enable linger for boot persistence
10. Install CLI tool to `~/.local/bin/inframatik`
11. Start the inframatik service
12. Set admin password via local API
13. If `--enroll` provided: enroll with master, configure as worker, restart

## Error Handling

| Scenario | Handling |
|----------|---------|
| Worker heartbeat to unknown master | Retry with exponential backoff (5s-30s) |
| Master returns 404 on heartbeat | Worker re-registers |
| Worker offline for >45s | Master marks status "offline" |
| Proxy request to unreachable worker | 502: "Node unreachable" |
| Proxy request returns error | 502 with worker's error message |
| Invalid enrollment token | 401: "Invalid or expired enrollment token" |
| Invalid API key on register | 401: "Unknown API key" |
| Update package too large (>50MB) | 413: "Package too large" |
| Path traversal in update package | 400: "Unsafe path in package" |
| Init when already configured | 400: "Node already configured. Reset first." |

## Background Tasks

Both tasks are started in the FastAPI lifespan context manager and cancelled on shutdown:

| Task | Role | Interval | Purpose |
|------|------|----------|---------|
| `stale_checker_loop` | master | 10s | Mark nodes with `last_seen > 45s ago` as offline |
| `heartbeat_sender_loop` | worker | 15s (after registration) | Register with master then send periodic heartbeats |

## Decisions

| Decision | Alternatives Considered | Why This Choice |
|----------|------------------------|-----------------|
| In-memory node registry | Database, config file | Nodes are ephemeral state. Lost on restart is acceptable since workers re-register. |
| 15s heartbeat / 45s stale | 5s/15s, 30s/90s | Balances responsiveness with network overhead. 3 missed heartbeats before offline. |
| Enrollment tokens (one-time) | Shared secret, mTLS, manual API key exchange | Simple, secure. No shared secrets. Token consumed prevents replay. |
| Master URL from Host header | Config-based, hardcoded | Install script auto-detects master URL from the request that fetched it. |
| tar.gz for code deployment | git pull, rsync, Docker | No git required on workers. Self-contained package. Path safety validated. |
| `_id_map` dual-mapping | Single ID system, UUID-only | Workers generate their own IDs; master assigns config IDs. Map resolves both. |
| Worker address auto-detection | Manual config, mDNS | UDP socket trick gives the routable IP toward the master. Works across subnets. |
