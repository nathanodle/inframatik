# Service Management Specification

**Status:** Complete

## Overview

inframatik manages long-running processes as systemd user services. Each registered service gets a dedicated port from the 8000-8999 range, a systemd unit file with environment variables, and optional Cloudflare tunnel integration. Services are tracked in a JSON registry file and controlled via `systemctl --user` commands.

## Requirements

1. **Unique names** -- Service names must be unique within a node's registry.
2. **Auto port assignment** -- Ports allocated sequentially from 8000-8999. No manual port selection.
3. **Systemd integration** -- Each service gets a unit file under `~/.config/systemd/user/` with the `infra-` prefix.
4. **Environment variables** -- Every service receives `PORT` and `HOST` environment variables via its unit file.
5. **Input validation** -- Service names, commands, and working directories are validated before registration.
6. **Atomic port reservation** -- Port is written to the registry file before any async operations to prevent races.
7. **CF integration** -- When a hostname is provided, tunnel route + DNS record + Access app are created automatically.
8. **Clean deregistration** -- Stopping, disabling, removing the unit file, and cleaning up CF resources on delete.

## Service Lifecycle

```
Register (POST /api/services)
  -> Validate inputs (name, command, working_dir)
  -> Allocate next available port
  -> Write to services.json registry (reserves port)
  -> Generate ports.env file
  -> Write systemd unit file to ~/.config/systemd/user/infra-{name}.service
  -> daemon-reload
  -> [Optional] Create CF tunnel route + DNS + Access app
  -> Return service info (status: "inactive")

Start (POST /api/services/{name}/start)
  -> systemctl --user enable --now infra-{name}.service
  -> Return current status

Stop (POST /api/services/{name}/stop)
  -> systemctl --user disable --now infra-{name}.service
  -> Return current status

Restart (POST /api/services/{name}/restart)
  -> systemctl --user restart infra-{name}.service
  -> Return current status

Deregister (DELETE /api/services/{name})
  -> systemctl --user disable --now infra-{name}.service
  -> Delete unit file
  -> daemon-reload
  -> [Optional] Remove CF tunnel route + DNS + Access app
  -> Remove from services.json
  -> Regenerate ports.env
```

## Port Assignment

| Property | Value |
|----------|-------|
| Range | 8000-8999 (1000 ports) |
| Allocation | Sequential -- first unused port in range |
| Storage | `services.json` registry and `ports.env` file |
| Environment | `$PORT` in unit file, `$INFRA_{NAME}_PORT` in ports.env |

### ports.env Format

Auto-generated file at `~/.config/inframatik/ports.env`, sourced from `.bashrc`:

```bash
# Auto-generated by inframatik -- do not edit
export INFRA_MY_APP_PORT=8000
export INFRA_ANOTHER_SVC_PORT=8001
```

Variable name derivation: `INFRA_` + name with hyphens replaced by underscores, uppercased + `_PORT`.

### Port Exhaustion

If all 1000 ports are allocated, `next_available_port()` returns `None` and registration fails with HTTP 400: "No ports available in range 8000-8999".

## Systemd Unit Template

```ini
[Unit]
Description=infra: {name}
After=network-online.target

[Service]
Type=simple
WorkingDirectory={working_dir}
ExecStart={command}
Restart=on-failure
RestartSec=5s
Environment=PORT={port}
Environment=HOST={host}

[Install]
WantedBy=default.target
```

| Field | Value |
|-------|-------|
| `{name}` | Service name from registration |
| `{working_dir}` | Resolved absolute path (expanded, resolved) |
| `{command}` | User command with `%` escaped to `%%` |
| `{port}` | Allocated port number |
| `{host}` | `0.0.0.0` if LAN-accessible, `127.0.0.1` otherwise |

Unit file path: `~/.config/systemd/user/infra-{name}.service`

## Input Validation

### Service Name

- Regex: `^[a-z0-9][a-z0-9_-]*$`
- Maximum length: 48 characters
- Must start with lowercase alphanumeric
- Allowed characters: lowercase letters, digits, hyphens, underscores

### Command

- Must not be empty
- Must not contain newlines (`\n`, `\r`)
- Must not contain semicolons in dangerous positions (` ; `, starts with `; `, ends with ` ;`) -- systemd interprets `;` as command separators
- `%` characters escaped to `%%` to prevent systemd specifier expansion

### Working Directory

- Must not contain newlines
- Path is expanded (`~` expansion) and resolved to absolute
- Must exist as a directory at registration time

## CF Integration on Registration

When a `hostname` is provided during service registration:

1. **Tunnel route**: `add_tunnel_route(hostname, port)` -- adds ingress rule to the node's CF tunnel
2. **DNS record**: `create_dns_record(hostname)` -- creates proxied CNAME pointing to tunnel
3. **Access app**: `create_access_app(name, hostname, policy_id)` -- creates CF Access app with default policy (only if `cf_default_policy_id` is configured)

On deregistration, the reverse operations are performed:
1. `remove_tunnel_route(hostname)`
2. `delete_dns_record(hostname)`
3. `delete_access_app(hostname)`

CF failures during registration are logged but do not prevent the service from being created. CF failures during deregistration are silently ignored (best-effort cleanup).

## API Endpoints

### `GET /api/services`

List all registered services with their current systemd status.

**Response:** Array of service objects.

```json
[
  {
    "name": "my-app",
    "port": 8000,
    "command": "uvicorn main:app",
    "working_dir": "/home/user/my-app",
    "hostname": "myapp.example.com",
    "lan": false,
    "status": "active"
  }
]
```

Status values come from `systemctl --user is-active`: `"active"`, `"inactive"`, `"failed"`, `"activating"`, etc.

**Scoped service tokens** see only their own service filtered from the list.

### `POST /api/services`

Register a new service.

**Request body:**

```json
{
  "name": "my-app",
  "command": "uvicorn main:app",
  "working_dir": "/home/user/my-app",
  "hostname": "myapp.example.com",
  "lan": false
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | Service name (validated) |
| `command` | string | Yes | ExecStart command |
| `working_dir` | string | Yes | Working directory path |
| `hostname` | string | No | CF hostname for public access |
| `lan` | boolean | No | Bind to 0.0.0.0 instead of 127.0.0.1 (default: false) |

**Response (201):**

```json
{
  "name": "my-app",
  "port": 8000,
  "command": "uvicorn main:app",
  "working_dir": "/home/user/my-app",
  "hostname": "myapp.example.com",
  "lan": false,
  "status": "inactive",
  "unit": "infra-my-app.service",
  "cf_route_added": true
}
```

**Errors:**
- 400: Validation failure (name, command, working_dir), duplicate name, no ports available

### `DELETE /api/services/{name}`

Deregister a service. Stops, disables, removes unit file, cleans up CF resources.

**Response:**

```json
{
  "deleted": "my-app",
  "port": 8000,
  "command": "uvicorn main:app",
  "working_dir": "/home/user/my-app"
}
```

**Errors:**
- 404: Service not found

### `POST /api/services/{name}/start`

Enable and start a service.

**Response:**

```json
{
  "name": "my-app",
  "status": "active"
}
```

**Errors:**
- 404: Service not found
- 500: systemctl command failed

### `POST /api/services/{name}/stop`

Disable and stop a service.

**Response:** Same as start.

### `POST /api/services/{name}/restart`

Restart a running service.

**Response:** Same as start.

### `GET /api/services/{name}/logs`

Fetch recent journal logs for a service.

**Query parameters:**
- `lines` (int, default 100): Number of log lines to return

**Response:**

```json
{
  "name": "my-app",
  "logs": "Mar 07 12:00:00 server infra-my-app[1234]: Started\n..."
}
```

Logs are fetched via `journalctl --user -u infra-{name}.service -n {lines} --no-pager`.

**Errors:**
- 404: Service not found

### `GET /api/ports/next`

Return the next available port number (useful for pre-populating the UI).

**Response:**

```json
{
  "port": 8002
}
```

**Errors:**
- 503: No ports available

### Proxied Endpoints (Master)

| Endpoint | Proxied To |
|----------|-----------|
| `GET /api/nodes/{id}/services` | `GET /api/services` |
| `POST /api/nodes/{id}/services` | `POST /api/services` |
| `DELETE /api/nodes/{id}/services/{name}` | `DELETE /api/services/{name}` |
| `POST /api/nodes/{id}/services/{name}/{action}` | `POST /api/services/{name}/{start\|stop\|restart}` |
| `GET /api/nodes/{id}/services/{name}/logs` | `GET /api/services/{name}/logs?lines={n}` |

## Data Model

### services.json

Path: `~/.config/inframatik/services.json`

```json
{
  "my-app": {
    "port": 8000,
    "command": "uvicorn main:app",
    "working_dir": "/home/user/my-app",
    "hostname": "myapp.example.com",
    "lan": false
  },
  "worker-svc": {
    "port": 8001,
    "command": "python3 worker.py",
    "working_dir": "/home/user/worker",
    "hostname": null,
    "lan": true
  }
}
```

### Systemd Unit Files

Path: `~/.config/systemd/user/infra-{name}.service`

One file per registered service. Created on registration, deleted on deregistration.

### ports.env

Path: `~/.config/inframatik/ports.env`

Regenerated on every registry write. Sourced from `.bashrc` for shell access to service ports.

## UI Components

### Service Cards

Each service rendered as a `.service-card` in the `.services-list`:

```
[Status Dot] [Service Name] [Port Badge] [Hostname Link] [LAN/CF Badge]  [Start][Stop][Restart][Logs][Delete]
```

- Status dot: green (active), gray (inactive), red (failed)
- Port badge: monospace pill showing port number
- Hostname link: clickable `https://{hostname}` link (if hostname set)
- LAN badge: yellow "LAN" tag (if `lan: true`)
- CF badge: blue "CF" tag (if hostname set)

### New Service Modal

Modal form with fields:
- **Name**: text input, placeholder "my-app"
- **Command**: text input, placeholder "uvicorn main:app"
- **Working Directory**: text input, placeholder "/home/user/my-app"
- **CF Hostname**: optional text input, placeholder "myapp.example.com"
- **LAN accessible**: checkbox with hint "bind to 0.0.0.0 instead of localhost"
- **Port preview**: shows the next available port before submission

### Logs Modal

Wide modal (720px) with:
- Title: "Logs: {service-name}"
- Monospace content area (JetBrains Mono, 12px, max-height 60vh, scrollable)
- Close button

## Error Handling

| Scenario | Handling |
|----------|---------|
| Duplicate service name | 400: "Service '{name}' already exists" |
| Invalid name format | 400: Regex validation message |
| Name too long (>48 chars) | 400: "Name must be 48 characters or less" |
| Empty command | 400: "Command must be a single line" |
| Command with newlines | 400: "Command must be a single line" |
| Command with semicolons | 400: "Command cannot contain semicolons" |
| Working dir doesn't exist | 400: "Working directory does not exist: {path}" |
| No ports available | 400: "No ports available in range 8000-8999" / 503 from `/api/ports/next` |
| systemctl start fails | 500: "Failed to start: {output}" |
| systemctl stop fails | 500: "Failed to stop: {output}" |
| CF route creation fails | Logged, service still created. `cf_route_added: false` |
| CF cleanup on delete fails | Silently ignored (best-effort) |

## Decisions

| Decision | Alternatives Considered | Why This Choice |
|----------|------------------------|-----------------|
| Sequential port allocation | Random, user-chosen, hash-based | Simple, predictable, no collisions. 1000 ports is sufficient. |
| Port reserved before async ops | Reserve after CF setup | Prevents race condition where two services could get the same port during concurrent registrations. |
| `enable --now` for start | `start` only | Ensures service survives reboot. User units with linger persist. |
| `disable --now` for stop | `stop` only | Prevents auto-restart after reboot. Consistent with `enable --now` for start. |
| `%` escaped to `%%` in commands | Block `%` entirely, no escaping | Allows users to use `%` in commands (e.g., Python format strings) without breaking systemd. |
| Semicolons blocked in commands | Allow all, full escaping | systemd interprets `;` as command separators. Blocking prevents unexpected behavior. |
| CF failures non-fatal on register | Fail registration on CF error | Service should work locally even if CF setup fails. CF can be configured manually later. |
| Registry in JSON file | SQLite, systemd unit parsing | Consistent with node.json approach. Simple, fast reads. Unit files don't store all metadata. |
